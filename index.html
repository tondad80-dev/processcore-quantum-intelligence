How the claim check is bounded

The installed module reports SUPPORTED, MISMATCH, UNKNOWN, STALE or UNVERIFIED for selected scalar fields from permitted read-only adapters. It checks both value and type; source inspections have a 300-second freshness limit. The inspection time is distinct from the time of a historical test.

The new Factory job’s result and delivery are adopted as claim evidence. Its code has not thereby been integrated into a product. This interface checks structured fields, not arbitrary prose, and always returns execution_authorized=false.

On 14 October, all 12 claim-gate manifest files and the launcher matched their installation records. The separate scoped ProcessCore 1.0.0 acceptance does not turn these structured-field checks into verification of arbitrary prose.

Control-path invariant: ACTUAL_STATE ≠ EXPECTED_STATE ≠ POLICY_DECISION ≠ AUTHORIZATION ≠ EFFECT. Detecting a difference does not create permission to change it.
Reuse — when earlier work can inform a new task

Use earlier work with explicit limits.

Module 0.1.3-rc.1 checks 12 modeled conditions against an explicit contract for a new job. Its reviewed profiles currently cover the NORMALIZE and SUMMARY candidates. A matching result can supply reference context for new generation; it does not transfer the earlier task's authorization.

Fresh acceptance required: the check is advisory, supported by bounded tests and code review. It is not a formal proof, automatic execution permission or measured token-saving result. Unsupported requirements remain reference-only.
Runtime control — detecting a change and authorizing an action

Detection, policy and authorization are separate.

Current research keeps actual state, expected state, policy decision, authorization and effect as distinct boundaries. A system may detect drift and even produce a policy decision without thereby gaining authority to change reality.

Persistence boundary: one successful bounded invocation is still not continuing execution authority. PERSISTENCE ≠ ACTIVATION ≠ EXECUTION AUTHORITY ≠ EFFECT.

Actual vs expected

Observed state is evidence. Expected state comes from valid project-scoped authority. Their difference is a classification result, not remediation authority.

Policy decision

A deterministic policy decision may establish whether an effect is eligible for consideration. It does not itself authorize the effect.

Authorization + effect

Any state-changing effect requires separate explicit authorization. If an effect occurs, its receipt and post-effect observation must remain independently inspectable and create new evidence.

Version boundary: this post-v0.4 work remains bounded research and validation. The bounded no-effect invocation is not proof of general runtime readiness, not a declared ProcessCore v0.5 release, not live autonomous remediation and not a production-readiness claim.
Validation — checking the rules as well as the result

Validation is not authority.

ProcessCore has repeatedly preserved validator failures for read-only reconciliation rather than treating a red result as automatic proof that the underlying implementation or authoritative state is wrong.

Documented reconciliations have shown cases where the authoritative contract remained coherent while a validator expected a different representation. The validation logic itself therefore becomes part of the audit surface.

evidence ≠ validation

Evidence exists independently of the rule set used to test it.

validation ≠ authority

A red validator result does not automatically redefine the authoritative project state.

authority ≠ interpretation

Authority is established before downstream human or AI interpretation.

Claim boundary: “Validation is not authority” is presented here as a ProcessCore architectural conclusion from documented project cases, not as a quotation from an external standard.
